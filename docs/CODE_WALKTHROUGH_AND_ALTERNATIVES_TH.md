# คู่มือเข้าใจโค้ด Pacman Project 0–2: ทำงานอย่างไร ทำไมเลือกวิธีนี้ และทางเลือกอื่น

เอกสารนี้อ่านได้โดยไม่ต้องเปิดโค้ดพร้อมกันทุกไฟล์ แต่ชื่อฟังก์ชันและพฤติกรรมอ้างอิงจากไฟล์ใน repository นี้โดยตรง จุดประสงค์คือให้ตอบได้ทั้ง **โค้ดทำอะไร**, **หลักการที่รองรับ**, **เหตุผลที่เลือก**, และ **ถ้าเปลี่ยนวิธีจะแลกกับอะไร** หากต้องการรายละเอียดสมการและขอบเขตเชิงลึกอีกชั้น อ่าน [คำอธิบายโค้ดเดิม](CODE_EXPLANATION_TH.md) คู่กัน

## 1. เริ่มจากภาพรวม

| ส่วน | ปัญหา | สิ่งที่รู้ | ผลที่ต้องคืน | วิธีหลัก |
|---|---|---|---|---|
| Project 0 | เก็บอาหารทั้งหมด | แผนที่ อาหาร แคปซูล และตำแหน่ง Pacman | การเดินหนึ่งก้าวในแต่ละตา | BFS, A* |
| Project 1 | เก็บอาหารและหลบผี | สถานะจริงและ legal actions ของผีหนึ่งตัว | การเดินหนึ่งก้าว | Minimax, H-Minimax |
| Project 2 | ตำแหน่งผีมองไม่เห็น | แผนที่ แบบจำลองผี และระยะจากเซนเซอร์มี noise | belief ของผีแต่ละตัว | Bayes filter |
| โบนัส Project 2 | เดินไปกินผีที่มองไม่เห็น | ตำแหน่ง Pacman, legal actions, belief | การเดินหนึ่งก้าว | heuristic บน belief |

ลำดับร่วมกันคือ `run.py` โหลดแผนที่และเอเจนต์ → engine สร้าง `state` → เรียก `get_action` → engine ใช้คำตอบอัปเดตเกม → ทำซ้ำ ส่วนที่ต่างกันคือ Project 0 วางแผนล่วงหน้าทั้งเกม, Project 1 ต้องตอบสนองผี, และ Project 2 ต้องประมาณข้อมูลที่ซ่อนอยู่ก่อนเลือกการเดิน

คำพื้นฐานที่ควรรู้:

- **state** คือภาพรวมของเกม ณ ขณะหนึ่ง เช่น ตำแหน่งผู้เล่น อาหาร และผี
- **action** คือทิศที่จะเดิน เช่น North หรือ East
- **successor** คือ state หลังลองเดินหนึ่ง action โดยใช้ API ของ engine
- **frontier** คือสถานะที่พบแล้วแต่ยังไม่ได้ขยาย
- **belief** คือการแจกแจงความน่าจะเป็นของตำแหน่งผี ไม่ใช่พิกัดเดียว
- พิกัดและเมทริกซ์ใน Project 2 ใช้ `[x, y]` และ shape `(width, height)` โดย `(0, 0)` อยู่ล่างซ้าย

ไฟล์ `project0/`, `project1/`, `project2/` มี `pacman_module` ของตัวเอง ชื่อ API อาจเหมือนกัน แต่กติกาและ flags ของ runner ต่างกัน อย่าสลับ engine ข้ามโปรเจกต์ ไฟล์ ZIP ที่รากเป็นชุดเริ่มต้น ส่วนโค้ดที่ทำแล้วอยู่ในสามโฟลเดอร์โปรเจกต์

## 2. อ่าน state และสร้าง key ให้ถูก

เริ่มดู `key(state)` ใน [`bfs.py`](../project0/bfs.py), [`astar.py`](../project0/astar.py) และ [`minimax.py`](../project1/minimax.py) ก่อนอ่าน search loop เพราะ key เป็นนิยามว่า **สถานะสองอันถือว่าเหมือนกันเมื่อใด**

Project 0 ใช้ `(ตำแหน่ง Pacman, อาหารที่เหลือ, แคปซูลที่เหลือ)` ถ้าใช้แค่ตำแหน่ง Pacman จะผิด: กลับมายืนช่องเดิมหลังเก็บอาหารแล้วเป็นงานคนละสถานะ แต่ถ้าใส่คะแนนสะสมและเวลาทั้งหมดลง key จะทำให้สถานะที่มีอนาคตเหมือนกันถูกแยกเป็นหลายอัน จนการค้นหาช้าหรือวนไม่จบ Project 1 เพิ่มพิกัดผี ทิศผี ผู้ที่จะเดิน และสถานะจบ เพราะตำแหน่งผีเดิมแต่หันคนละทิศอาจมี legal actions คนละชุด

ทั้งสามเอเจนต์ค้นหาสถานะเกมด้วย `generatePacmanSuccessors()` หรือ `generateGhostSuccessors(1)` เพื่อให้กฎเกมและการนับ expanded nodes เป็นของ engine ส่วนการคำนวณระยะบนกำแพงด้วย BFS พิกัดเป็นงานภายใน heuristic ไม่ใช่การเดินในเกมจริง

**ทางเลือก:** ใช้ `state` ทั้งก้อนเป็น key ได้ก็ต่อเมื่อพิสูจน์ได้ว่าการเปรียบเทียบและ hash ของมันตรงกับสิ่งที่กำหนดอนาคต การใช้ key ที่เล็กเกินไปทำให้รวมสถานะที่ควรแยก; key ที่ใหญ่เกินไปทำให้ค้นหาซ้ำมากขึ้น

## 3. Project 0 — หาเส้นทางเมื่อโลกไม่เปลี่ยน

### 3.1 BFS ใน `project0/bfs.py`

`PacmanAgent.__init__` สร้าง `moves` เป็น `deque` และ `planned=False` เมื่อ engine เรียก `get_action` ครั้งแรก เอเจนต์เรียก `search(state)` หาเส้นทางกินอาหารครบทั้งเส้น เก็บใน `moves` จากนั้นแต่ละตาดึง action ตัวหน้าออกมา ถ้าแผนหมดแล้วคืน `STOP` ตัวแปร `planned` สำคัญเพราะแผนว่างอาจหมายถึง “เริ่มมาก็ชนะแล้ว” ไม่ใช่ “ยังไม่ได้วางแผน”

ใน `search` จะใส่ state เริ่มในคิวแบบ FIFO และเก็บ `parents[start]=None` ทุกครั้งที่ดึงหัวคิว จะตรวจว่าชนะหรืออาหารหมดหรือยัง ถ้ายังจะขยาย successor ของ Pacman แล้วใส่ state ที่ไม่เคยพบเข้าท้ายคิว การทำเครื่องหมายว่า “พบแล้ว” ตั้งแต่ตอนใส่คิวป้องกันสถานะเดียวกันเข้าคิวหลายครั้ง เมื่อถึงเป้าหมายก็เดินย้อน `parents` เพื่อได้ action ทั้งเส้น ถ้าไม่มีทางเก็บอาหารครบจะโยน `ValueError`

หลักการคือทุก action มีต้นทุนหนึ่งก้าว FIFO จึงขยายเส้นทางยาว 0, 1, 2, ... ตามลำดับ เป้าหมายแรกที่ดึงได้ใช้ **ก้าวน้อยที่สุด** บนกราฟสถานะนี้ ไม่ได้แปลว่าคะแนนมากที่สุดเสมอไป เพราะการกินแคปซูลหักเพิ่ม 5 คะแนน

| ถ้าใช้วิธีอื่น | ผลที่อาจเกิด |
|---|---|
| DFS/stack | อาจเจอคำตอบเร็วในบางแผนที่ แต่ไม่มีหลักประกันว่าทางสั้นหรือคะแนนดี |
| `list.pop(0)` แทน `deque.popleft()` | ใช้ได้เชิงผลลัพธ์ แต่ต้องเลื่อนสมาชิก list ทุกครั้ง ทำให้คิวใหญ่ช้าลง |
| เก็บ path ทั้งเส้นในทุกคิว | อ่านง่าย แต่คัดลอก action ซ้ำและใช้หน่วยความจำมากกว่า `parents` |
| ค้นใหม่ทุกตา | ผลเทียบเท่าในโลกคงที่ถ้าค้นถูก แต่เสียเวลาคำนวณซ้ำ |

### 3.2 A* ใน `project0/astar.py`

โจทย์ส่วนนี้ให้คะแนนอาหารที่เก็บครบเป็นค่าคงที่ระหว่างเส้นทางที่ชนะ ทุกก้าวเสีย 1 และการกินแคปซูลเสียเพิ่ม 5 การเพิ่มคะแนนสุดท้ายจึงเท่ากับลดต้นทุน `จำนวนก้าว + 5 × จำนวนแคปซูลที่กิน` โค้ดไม่ใช้ `-คะแนน` ตรง ๆ เป็นต้นทุน เพราะรางวัลจากอาหารทำให้ขอบบางอันติดลบ ซึ่งขัดกับสมมติฐานของการค้นหาแบบ Dijkstra/A* ที่ใช้

`prepare(state)` ใช้ BFS บนกริดกำแพงจากอาหารแต่ละจุดเพื่อเก็บระยะทางจริงผ่านทางเดิน `heuristic(state)` เอาระยะจาก Pacman ไปอาหารที่ใกล้ที่สุด บวกน้ำหนักต้นไม้แผ่ทั่วขั้นต่ำ (MST) ที่เชื่อมอาหารที่เหลือ ค่านี้เป็น **ขอบล่าง** ของงานที่ยังต้องทำ: ต้องไปถึงอาหารสักจุด และต้องเชื่อมอาหารทุกจุดเข้าด้วยกัน ค่าปรับแคปซูลในอนาคตที่ไม่แน่ใจจะเกิดถูกละไว้ ทำให้ heuristic ไม่บวกต้นทุนที่อาจไม่ได้จ่าย

`search` เก็บ `g` ที่ดีที่สุดของแต่ละ key ใน `best` และจัดคิว priority ด้วย `f=g+h` ถ้าเจอทางที่ถูกกว่าสำหรับ key เดิมก็อัปเดต `best` กับ `parents` แล้วใส่คิวใหม่ รายการคิวเก่าที่ล้าสมัยถูกข้ามเมื่อดึงออกมา `serial` ใช้ตัดสินลำดับเมื่อ `f` เท่ากันโดยไม่ต้องให้ Python เปรียบเทียบ object ของ state การ cache `trees` ลดการคำนวณ MST ซ้ำสำหรับชุดอาหารเดิม

ตัวอย่าง: เส้นทาง 4 ก้าวที่กินแคปซูลหนึ่งเม็ดมีต้นทุน 9 ส่วนทางอ้อม 6 ก้าวที่ไม่กินแคปซูลมีต้นทุน 6 BFS จะเลือกทาง 4 ก้าว ส่วน A* ที่ใช้ต้นทุนนี้เลือกทาง 6 ก้าวและได้คะแนนมากกว่า หาก heuristic เป็นขอบล่างที่ถูกต้อง A* ให้เส้นทางต้นทุนต่ำสุดภายใต้โจทย์นี้

| ถ้าเปลี่ยน | ผลที่อาจเกิด |
|---|---|
| ตั้ง `h=0` | กลายเป็น Dijkstra: ยังหาต้นทุนต่ำสุด แต่โดยทั่วไปขยายสถานะมากขึ้น |
| ใช้ Manhattan distance | คำนวณถูกกว่าและยังเป็นขอบล่าง แต่ไม่เห็นกำแพง จึงมักนำทางได้อ่อนกว่า |
| ใช้ heuristic ที่สูงเกินต้นทุนจริง | อาจเร็วขึ้น แต่เสียหลักประกันคำตอบเหมาะที่สุด |
| ไม่เก็บ `best` และไม่ยอมเปิด key เดิมอีก | อาจเก็บเส้นทางแพงกว่าไว้เมื่อพบทางถูกกว่าทีหลัง |
| คิดแคปซูลทุกเม็ดใน heuristic | จะผิดหากมีทางชนะที่ไม่ต้องกินเม็ดนั้น และอาจทำให้ heuristic สูงเกินจริง |

### 3.3 DFS ใน `project0/dfs.py`

โค้ดเติม `key()` และ `dfs()` ที่ขาดจากชุดเริ่มต้น โดยใช้ stack แบบ LIFO เพื่อสาธิตการค้นหาอีกแบบ DFS ไม่อยู่ในไฟล์บังคับส่ง Project 0 และไม่รับประกันระยะทางหรือคะแนนที่ดีที่สุด ใช้เทียบว่าลำดับการขยายสถานะมีผลต่อคำตอบอย่างไร

## 4. Project 1 — ตัดสินใจเมื่อผีตอบโต้ได้

Pacman เป็นฝ่ายเลือกทางที่ดีที่สุดสำหรับตน ส่วน Minimax ให้ผีเลือกทางที่เสียที่สุดสำหรับ Pacman จาก **legal actions ทั้งหมด** จึงเป็นการตัดสินใจแบบ worst case ไม่ได้แปลว่าผีจริงจะเดินฉลาดที่สุดเสมอ ผีจริงใน benchmark มี `dumby`, `greedy`, `smarty` แต่เอเจนต์ไม่อาศัยการรู้ policy ของผีล่วงหน้า

### 4.1 Exact Minimax ใน `project1/minimax.py`

ถ้าเขียน recursion ไปจนชนะ/แพ้ เกมอาจวนกลับ state เดิมโดยอาหารไม่เปลี่ยนและ recursion ไม่จบ `solve(initial)` จึงทำสองช่วง: สร้าง **กราฟสถานะที่เข้าถึงได้ทั้งหมด** ด้วยคิว แล้วแก้ค่าจากสถานะจบย้อนกลับ เรียกวิธีนี้ว่า retrograde analysis

คะแนนถูกแปลงเป็นต้นทุนเพื่อใช้คำนวณง่าย: ขอบที่ Pacman เดินเพิ่ม 1, ขอบที่ผีเดินเพิ่ม 0, ชนะมี terminal cost 0, แพ้มี terminal cost `1000 + 10 × อาหารที่เหลือ` ดังนั้น Pacman เลือกค่าต่ำสุด ผีเลือกค่าสูงสุด การวนเล่นไม่จบให้ต้นทุนอนันต์ เพราะเสียคะแนนจากเวลาไปเรื่อย ๆ การแปลงนี้ใช้กับขอบเขต **ผีหนึ่งตัว ไม่มีแคปซูล** ตามโจทย์ส่วนนี้

ช่วงสร้างกราฟเก็บ `outgoing` เพื่อเลือก action, `predecessors` เพื่อรู้ว่า child ส่งผลต่อ parent ใด, `remaining` เพื่อนับ child ของตาผีที่ยังไม่รู้ค่า และ `worst` เพื่อสะสมค่าแย่ที่สุด ช่วงแก้ย้อนเริ่มจาก terminal states ใน min-heap เมื่อรู้ค่าของ child แล้ว ฝ่าย Pacman สามารถเสนอทางเลือกนั้นได้ทันทีเพราะต้องการค่าต่ำสุด ฝ่ายผีต้องรอ child **ทุกตัว** จึงรู้ค่าสูงสุดแน่นอน โหนดที่ยังแก้ไม่ได้เมื่อคิวหมดให้ค่า infinity แล้วเก็บ `policy` เป็น action ที่ชี้ไป child ค่าต่ำสุด

`get_action` ใช้ policy ที่แก้ไว้ ถ้า state ปัจจุบันอยู่นอกกราฟที่ cache ก็เรียก `solve` ใหม่ ถ้าจบเกมแล้วคืน `STOP` วิธีนี้ให้ค่า worst case ของกราฟที่สร้างครบ แต่ใช้หน่วยความจำมากและเหมาะกับแผนที่เล็ก

| ถ้าเปลี่ยน | ผลที่อาจเกิด |
|---|---|
| recursion จนจบโดยไม่จัดการวงรอบ | อาจวนไม่สิ้นสุด |
| ตัดวงรอบแล้วตั้งค่า 0 เอง | อาจเลือกนโยบายผิด เพราะ 0 ไม่มีความหมายเป็นมูลค่าอนาคตของ state นั้น |
| จำกัดความลึก | ประหยัดทรัพยากร แต่กลายเป็น H-Minimax และต้องประเมินใบไม้ที่ยังไม่จบ |
| จำลองผีจาก policy ที่รู้จัก | อาจได้คะแนนดีกับผีชนิดนั้น แต่เสียหลักประกัน worst case เมื่อ policy เปลี่ยน |
| ไม่ใส่ทิศผีใน key | รวม state ที่ผีมี legal actions ต่างกัน ทำให้กราฟผิด |

### 4.2 H-Minimax ใน `project1/hminimax.py`

แผนที่ใหญ่เกินกว่าจะสร้างกราฟครบทุก state `get_action` จึงค้นใหม่ทุกตาจาก state ล่าสุด โดย default มองล่วงหน้า 4 **รอบ Pacman–ผี**: `value` ลด `depth` หลังตาผี ไม่ลดหลังทุก action ถ้าชนะหรือแพ้ระหว่างทางจะหยุดก่อนครบ depth

ใบไม้ที่ยังไม่จบใช้ `evaluate(state)` ให้คะแนนจาก `state.getScore()` หักอาหารที่เหลือ ระยะผ่านเขาวงกตไปอาหารใกล้สุด ความเสี่ยงจากระยะผี และจำนวนครั้งที่เคยมา `(ตำแหน่ง, ชุดอาหาร)` เดิม สถานะชนะ/แพ้ได้ค่ามาก/น้อยพิเศษ `distance_map` ใช้ BFS บนกำแพงและ cache ตามจุดเริ่ม เพราะกำแพงในเกมไม่เปลี่ยน `visits` ใช้ลดอาการเดินวนใน horizon สั้น

ใน `value` ตา Pacman ใช้ `max`; ตาผีใช้ `min` ค่าขอบ `alpha` และ `beta` บอกว่าบรรพบุรุษมีทางเลือกดีหรือแย่เท่าใดแล้ว เมื่อ `alpha >= beta` กิ่งที่เหลือเปลี่ยนคำตอบของบรรพบุรุษไม่ได้ จึงหยุดตรวจได้ โค้ดเรียง successor ด้วย `evaluate` ก่อน เพื่อให้พบกิ่งที่ทำให้ตัดได้เร็วขึ้น `cache` เก็บเฉพาะค่าที่อยู่ภายในหน้าต่าง alpha-beta เดิม ซึ่งเป็นค่าที่แน่นอน ไม่เก็บผล cutoff ที่อาจเป็นเพียงขอบ ล้าง cache ทุกตาเพราะ `visits` เปลี่ยนค่าประเมิน

| ถ้าเปลี่ยน | ผลที่อาจเกิด |
|---|---|
| ใช้ Minimax ไม่ prune แต่ depth เท่าเดิม | คำตอบควรเท่าเดิม แต่ขยายกิ่งมากกว่า |
| เพิ่ม depth | เห็นผลระยะไกลขึ้น แต่เวลาโตเร็วตามจำนวน action ที่แตกกิ่ง |
| ลด depth | เร็วขึ้น แต่อาจมองไม่เห็นผีหรืออาหารที่อยู่พ้น horizon |
| ใช้ระยะ Manhattan แทนระยะผ่านกำแพง | ถูกกว่า แต่บางครั้งประเมินว่าของอยู่ใกล้ทั้งที่กำแพงขวาง |
| cache ค่า cutoff เป็นค่า exact | อาจนำขอบผิดไปใช้เป็นคำตอบจริงใน state อื่น |
| ปรับน้ำหนัก heuristic | เปลี่ยนพฤติกรรมได้ แต่ไม่มีหลักประกันว่าจะดีขึ้นทุก layout ต้องทดสอบ |

## 5. Project 2 — Bayes filter สำหรับผีที่มองไม่เห็น

โค้ดหลักอยู่ใน [`project2/bayesfilter.py`](../project2/bayesfilter.py) `BeliefStateAgent` เก็บ `beliefGhostStates` เป็น list ของเมทริกซ์ `[x, y]` แยกตามผี ผีที่ยังอยู่มีผลรวมความน่าจะเป็น 1 และช่องกำแพงเป็น 0 ผีที่ถูกกินแล้วต้องคืนเมทริกซ์ศูนย์ `get_action` ของ template เรียก `_get_evidence` → `update_belief_state` → `_record_metrics` แล้วส่ง `(belief ใหม่, evidence)` ให้ engine ฟังก์ชัน `get_action`, `_get_evidence`, `update_belief_state` เป็นส่วนที่โจทย์ห้ามแก้ จึงเติม logic ใน helper ที่เรียกต่อ

### 5.1 Sensor model: `_get_sensor_model`

เซนเซอร์ไม่ได้ให้ระยะตรง ๆ แต่ให้ `e = d + K - n/2` โดย `d` เป็น Manhattan distance, `K ~ Binomial(n, 0.5)` และ `n = int(4 × sensor_variance)` จากนั้นสำหรับทุกช่อง `(x,y)` คำนวณ `P(e | ผีอยู่ช่องนั้น)` ด้วย `binom.pmf(e-d+n/2, n, 0.5)` และกำหนด likelihood บนกำแพงเป็น 0 โค้ดใช้ NumPy broadcasting คำนวณทั้งกริดพร้อมกัน

ใช้ **Manhattan** ตรงนี้เพราะมันเป็นนิยามของเซนเซอร์ใน engine แม้มีกำแพงกั้น หากใช้ระยะทางผ่านเขาวงกตแทนจะดูสมจริงกว่าในบางบริบท แต่จะเป็นโมเดลที่ไม่ตรงกับค่าที่ engine สุ่มจริง และ belief อาจเบ้ `n` ถูกตัดเป็นจำนวนเต็ม จึงควรแยก “variance ที่ขอ” กับ variance จริง `n/4` ค่า evidence บางกรณีเป็นครึ่งจำนวนเต็มหรือติดลบได้ ไม่ควรปัดหรือบังคับให้ไม่ติดลบ

### 5.2 Transition model: `_get_transition_model`

ผลเป็น tensor `T[new_x, new_y, old_x, old_y]` สำหรับแต่ละช่องต้นทางที่เดินได้ จะดูเพื่อนบ้านสี่ทิศที่ไม่ชนกำแพง แล้วให้น้ำหนักทางที่ระยะจาก Pacman **ไม่ลดลง** เป็น 1, 2 หรือ 8 ตามชนิด `confused`, `afraid`, `scared`; ทางที่เข้าใกล้ให้น้ำหนัก 1 หารด้วยผลรวมน้ำหนักเพื่อได้ probability หากไม่มีเพื่อนบ้านให้คงที่เดิม ผลรวมของปลายทางจากช่องต้นทางที่เดินได้จึงเป็น 1

โมเดลขึ้นกับตำแหน่ง Pacman จึง cache เฉพาะเมื่อพิกัด Pacman เดิม ถ้าใช้ transition เดิมหลัง Pacman ย้าย ผีที่ `afraid` หรือ `scared` จะถูกทำนายตามแรงหนีจากจุดเก่า โค้ดคืน tensor หนาแน่นตาม API ที่โจทย์กำหนด จึงใช้หน่วยความจำประมาณ O(N²) เมื่อ N เป็นจำนวนช่องทั้งหมด หากออกแบบระบบขนาดใหญ่และเปลี่ยน API ได้ อาจเก็บเฉพาะ transition ที่ไม่เป็นศูนย์แบบ sparse เพื่อประหยัดพื้นที่

### 5.3 Bayes update: `_get_updated_belief`

สำหรับแต่ละผีที่ยังไม่ถูกกิน คำนวณทีละขั้น:

```text
prediction[new] = Σ_old T[new, old] × prior[old]
unnormalized[new] = prediction[new] × P(evidence | new)
posterior[new] = unnormalized[new] / Σ_new unnormalized[new]
```

ขั้นแรกคือ **Predict** ว่าผีอาจย้ายไปไหน ขั้นสองคือ **Correct** ด้วยเซนเซอร์ ขั้นสามคือ **Normalize** ให้รวมเป็น 1 โค้ด reshape tensor เป็นเมทริกซ์ หาเฉพาะ transition ที่ไม่เป็นศูนย์ แล้วใช้ `np.bincount` รวมมวลของปลายทาง จึงไม่ต้องคูณช่องศูนย์ทุกช่องสำหรับผีทุกตัว evidence เดียวกันในรอบนั้นใช้ sensor model ร่วมกันได้ แต่ prior ของแต่ละผีต้องแยกกัน ถ้าเฉลี่ย prior รวมกัน จะเสียตัวตนและประวัติของผีแต่ละตัว

ถ้าผีถูกกินจะคืนศูนย์ทันที ถ้าผลคูณ prediction กับ sensor รวมเป็นศูนย์ จะลองใช้ sensor บนช่องเดินทั้งหมด; ถ้า observation เป็นไปไม่ได้ทุกช่อง จะใช้ prediction; ถ้า prediction ก็ว่าง จะใช้ uniform บนช่องเดิน นี่เป็นวิธีฟื้นตัวเพื่อไม่ให้เกิดการหารศูนย์หรือ NaN **ไม่ใช่** posterior จาก Bayes ที่นิยามได้ในเหตุการณ์ probability zero

| ถ้าเปลี่ยน | ผลที่อาจเกิด |
|---|---|
| ใช้พิกัดที่น่าจะเป็นที่สุดจุดเดียว | ง่ายและเร็ว แต่ทิ้งความไม่แน่นอนหลายตำแหน่ง |
| ใช้ sensor อย่างเดียว ไม่ Predict | ไม่สะท้อนการเคลื่อนที่ของผี |
| Predict อย่างเดียว ไม่ Correct | ไม่ใช้ข้อมูลใหม่จากเซนเซอร์ ความไม่แน่นอนอาจเพิ่มเรื่อย ๆ |
| ไม่ Normalize | มวลไม่ใช่ความน่าจะเป็นและอาจเล็กลงจนเป็นศูนย์เชิงตัวเลข |
| ใช้ตำแหน่งจริงจาก engine ช่วย filter | ตัวเลขดูดีผิดจริง และผิดโจทย์ที่ผีมองไม่เห็น |
| ใช้ particle filter | อาจประหยัดบนพื้นที่ใหญ่มาก แต่มีความคลาดเคลื่อนจากจำนวนอนุภาคและต้องออกแบบการสุ่มใหม่ |

### 5.4 Metrics กับโบนัส

`_record_metrics` ใช้ตำแหน่งจริงของผี **เพื่อวัดผลเท่านั้น** ไม่ส่งกลับไปให้ filter หรือ controller `entropy = -Σ b log₂ b` วัดความกระจาย, `Brier = Σ(b - one_hot_truth)²` วัดว่าการแจกแจงใกล้ความจริงเพียงใด, `true_mass` คือมวลที่ตำแหน่งจริง, และ `expected_distance` คือระยะเฉลี่ยจาก belief ไปตำแหน่งจริง Entropy ต่ำอย่างเดียวอาจแปลว่ามั่นใจผิด จึงต้องดู Brier ด้วย

โบนัสใน [`project2/pacmanagent.py`](../project2/pacmanagent.py) อ่านเฉพาะตำแหน่ง Pacman, legal actions และ belief เมื่อทิศใดเดินไม่ได้ ณ จุดที่ยืน จะจำช่องข้างหน้าว่าเป็นกำแพง จากนั้นรวมมวลของผีทุกตัว สำหรับ action ที่ถูกกฎหมายแต่ละอัน จะทำ BFS บนแผนที่ที่เรียนรู้มา และให้คะแนนมวลผีที่อยู่ใกล้แบบ `exp(-distance/4)` บวกโอกาสเจอผีทันที หักค่าการเยือนช่องเดิมบ่อย ๆ เลือกคะแนนสูงสุด หากไม่เหลือ action ที่เดินได้คืน `STOP`

การถือช่องที่ยังไม่รู้ว่าผ่านได้อาจทำให้ระยะทางประเมินสั้นเกินจริง แต่ action ที่ส่งจริงถูกจำกัดด้วย legal actions ทุกตา การอ่าน `getWalls()` หรือ `getGhostPositions()` ตรง ๆ จะทำให้ controller รู้ข้อมูลที่ไม่ควรรู้ตามขอบเขตโบนัส ตัวคูณใน utility เป็น heuristic ที่ทดลองใช้ ไม่ใช่สูตรรับประกันจับผีเร็วที่สุด
