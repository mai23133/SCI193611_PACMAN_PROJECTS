# เหตุผลและการทำงานของโค้ดอย่างละเอียด

เอกสารนี้อธิบายโค้ดที่เพิ่มหรือเติมในงานนี้ โดยอ้างอิงพฤติกรรม engine ใน repository
คำสั่งติดตั้งและรันอยู่ใน [INSTALL_AND_RUN_TH.md](INSTALL_AND_RUN_TH.md)
ลำดับการทำงานและการแบ่งงานสามคนอยู่ใน [WORKFLOW_TH.md](WORKFLOW_TH.md)

## 1. คำศัพท์และข้อตกลงร่วม

**State** คือสถานะเกม ณ ขณะหนึ่ง เช่น Pacman อยู่ไหน อาหารเหลือที่ใด
ผีอยู่ไหนและหันทางไหน ส่วน **action** คือการเดินที่เลือกในตานั้น
**Successor** คือสถานะหลังทำ action หนึ่งครั้ง

พิกัดในเกมเป็น `(x, y)` จุด `(0, 0)` อยู่ล่างซ้าย
อาร์เรย์ใช้ `[x, y]` และ shape `(width, height)`
ไม่ใช่ `[row, column]` แบบภาพที่หลายคนคุ้นเคย

เอเจนต์ Project 0–1 ดึงข้อมูลจาก API ของ state
และขยายโหนดผ่าน `generatePacmanSuccessors()` / `generateGhostSuccessors(1)`
เพื่อให้ engine นับโหนดได้ตามเกณฑ์ของโจทย์
ไม่แก้ `countExpanded` หรือ `maximumExpanded` เพื่อทำให้ผลดูดีขึ้น

การคำนวณระยะทางบน wall grid เป็นงานของ heuristic ไม่ใช่การจำลองตาเกม
จึงใช้ BFS บนพิกัดจาก `getWalls()` ได้ แต่เมื่อขยายสถานะเกมจริงต้องผ่าน API

### 1.1 เหตุใดต้องสร้าง state key เอง

ถ้าใช้ state ทั้งก้อน อาจมีคะแนนสะสมและข้อมูลอื่นทำให้สถานะที่มีทางเลือกอนาคตเหมือนกัน
ถูกนับว่าแตกต่าง การเดินวนจึงอาจสร้าง state ไม่สิ้นสุด

Project 0 ใช้:

```text
(ตำแหน่ง Pacman, tuple ตำแหน่งอาหารที่เหลือ, tuple แคปซูลที่เหลือ)
```

อาหารและแคปซูลต้องอยู่ใน key เพราะกลับมาที่ช่องเดิมหลังเก็บอาหาร
ไม่ได้มีงานที่เหลือเหมือนเดิม ใช้ tuple เพื่อให้ hash ได้และไม่เปลี่ยนภายหลัง

Project 1 เพิ่มตำแหน่งผี ทิศผี และผู้เล่นที่จะเดิน
ทิศผีสำคัญเพราะผีห้ามกลับหลังหันถ้ายังมีทางอื่น
ตำแหน่งเดียวกันแต่คนละทิศจึงมี legal actions ต่างกัน

### 1.2 คะแนนกับต้นทุนต่างกันอย่างไร

ตาม engine การกินอาหารได้ 10 คะแนน ก้าวหนึ่งเสีย 1 คะแนน
กินแคปซูลเสีย 5 ชนะได้เพิ่ม 500 และแพ้เสีย 500

สำหรับ Project 0 ที่ต้องชนะและกินอาหารเริ่มต้นทั้งหมดจำนวน `F`:

```text
คะแนนสุดท้าย = คะแนนเริ่มต้น + 10F + 500 - จำนวนก้าว - 5 × แคปซูลที่กิน
```

ดังนั้นการเพิ่มคะแนนสูงสุดเท่ากับลด `จำนวนก้าว + 5 × จำนวนแคปซูลที่กิน`
การใช้ `-คะแนนที่เปลี่ยน` เป็น cost ตรง ๆ จะมีขอบต้นทุนติดลบเมื่อกินอาหาร
ซึ่งไม่เหมาะกับสมมติฐานของ Dijkstra/A* แบบที่ใช้
โค้ดจึงตัดรางวัลคงที่เมื่อชนะออก แล้วใช้ต้นทุนไม่ติดลบแทน

## 2. Project 0: BFS — `project0/bfs.py`

### 2.1 แนวคิด

Breadth-first search ขยายสถานะตามจำนวนก้าว: ชั้น 0, 1, 2, ...
เมื่อทุก action คิดเป็นหนึ่งก้าว เป้าหมายแรกที่พบย่อมใช้ก้าวน้อยที่สุด

เลือก `collections.deque` เพราะเพิ่มท้ายและนำออกหน้าคิวได้ O(1)
ไม่ใช้ `list.pop(0)` ที่ต้องเลื่อนสมาชิกใน list

### 2.2 โค้ดทำงานอย่างไร

1. `key(state)` แปลงสถานะเป็น tuple
2. `search(state)` เริ่มคิวด้วยสถานะเริ่มต้น
3. `parents[start] = None` ระบุว่าต้นทางไม่มี parent
4. ดึงหัวคิว ตรวจว่าชนะหรือไม่มีอาหารเหลือแล้วหรือไม่
5. ถ้ายัง ขยาย Pacman successors ผ่าน API
6. successor ที่ไม่เคยเจอจะบันทึก `(parent_key, action)` และเข้าท้ายคิว
7. เมื่อพบเป้าหมาย ไล่ parent ย้อนจากเป้าหมายถึงต้นทางแล้วกลับลำดับ
8. `get_action()` เก็บแผนใน deque และส่งการเดินออกทีละตา

บันทึกสถานะว่าเคยเจอตอนนำเข้าคิว เพื่อไม่ให้หลาย parent ส่งสถานะเดียวกันเข้าคิวซ้ำ
การเก็บ parent ประหยัดกว่าการคัดลอกเส้นทางทั้งเส้นให้ทุก successor

### 2.3 การรับประกันและข้อจำกัด

BFS ตัวนี้รับประกัน **จำนวนก้าวน้อยที่สุด** เมื่อมีทางชนะใน Project 0
ไม่ได้รับประกันคะแนนสูงสุดเมื่อเส้นทางสั้นต้องกินแคปซูลที่มีค่าปรับ
ตัวอย่าง เส้นทาง 4 ก้าวกินหนึ่งแคปซูลมี cost คะแนน 9
แต่เส้นทางอ้อม 6 ก้าวไม่กินแคปซูลมี cost 6 และได้คะแนนดีกว่า
test `test_capsule_cost_changes_optimal_route` ตรวจตัวอย่างนี้โดยตรง

นี่เป็นความต่างระหว่างวัตถุประสงค์ของ BFS แบบต้นทุนก้าวเท่ากัน
กับคะแนนเกมที่มีต้นทุนแคปซูลเพิ่ม A* ในไฟล์ถัดไปคิดค่าใช้จ่ายส่วนนี้ครบ

เวลาและหน่วยความจำของ BFS เป็น O(V+E) และ O(V)
เมื่อ V คือจำนวนสถานะที่เข้าถึงได้ และ E คือขอบของกราฟสถานะ
V อาจโตตามจำนวนชุดอาหารที่เหลือถึงระดับ `จำนวนช่อง × 2^F`

## 3. Project 0: A* — `project0/astar.py`

### 3.1 เหตุผลที่ใช้ A*

BFS ไม่รู้ว่าสถานะใดอยู่ใกล้การกินอาหารครบ
A* จัดลำดับด้วย `f(s) = g(s) + h(s)`:

- `g(s)` คือต้นทุนที่จ่ายจริงจากต้นทาง
- `h(s)` คือขอบล่างของต้นทุนที่ยังต้องจ่าย

ในงานนี้ `g` เพิ่ม 1 ต่อการเดิน และเพิ่มอีก 5 ถ้าการเดินนั้นกินแคปซูล
สำหรับเกมไม่มีผีและต้องกินอาหารครบ ต้นทุนนี้ตรงกับการเพิ่มคะแนนสูงสุด

### 3.2 Heuristic ที่ใช้

```text
h(s) = ระยะสั้นที่สุดจาก Pacman ไปอาหารใกล้สุด
       + น้ำหนัก Minimum Spanning Tree ของอาหารที่เหลือ
```

ระยะทางทุกตัวเป็นระยะตามช่องเดินที่หลบกำแพงแล้ว
`prepare()` ทำ BFS จากตำแหน่งอาหารแต่ละจุดเพื่อสร้าง distance maps
`heuristic()` คำนวณ MST ด้วยแนวคิด Prim และ cache ตามชุดอาหารที่เหลือ

เหตุผลที่ heuristic ไม่ประเมินสูงเกินจริง:

1. เส้นทางจริงต้องไปถึงอาหารจุดแรก ระยะไปอาหารใกล้สุดไม่เกินส่วนนี้
2. จากนั้นเส้นทางที่กินอาหารครบย่อมเชื่อมอาหารทุกจุดเข้าด้วยกัน
3. น้ำหนัก MST ไม่มากกว่าน้ำหนักเส้นทางเชื่อมทั้งหมดนั้น
4. heuristic ยังไม่คิดค่าปรับแคปซูล ทำให้เป็นขอบล่างของ cost จริงต่อไป

อาหารหมดแล้วคืน 0 ถ้าอาหารเข้าถึงกันไม่ได้ ระยะจะเป็น infinity
search จะหมด frontier แล้วแจ้งว่าไม่มีเส้นทาง

### 3.3 โครงสร้างข้อมูลและการอัปเดต

`heapq` เก็บ `(f, serial, g, state)`
`serial` เพิ่มทีละหนึ่ง ใช้แก้กรณี priority เท่ากัน
เพื่อไม่ให้ Python พยายามเปรียบเทียบวัตถุ GameState ด้วย `<`

`best[key]` บันทึก `g` ที่ดีที่สุดซึ่งเคยพบ
ถ้าพบเส้นทางถูกกว่า จะอัปเดต best และ parent พร้อมนำเข้าคิวอีกครั้ง
รายการเก่าใน heap ไม่ต้องลบทันที แต่เมื่อดึงออกจะข้ามถ้า g ไม่ตรง best
จึงรองรับการเปิดสถานะเดิมใหม่เมื่อพบเส้นทางที่ดีกว่า

ตรวจเป้าหมายตอนนำออกจาก priority queue หลังข้ามรายการล้าสมัย
ไม่หยุดทันทีเมื่อเพิ่งสร้าง goal successor เพราะเส้นทางนั้นอาจยังแพงกว่าอีกทาง

### 3.4 ประสิทธิภาพ

การเตรียมระยะทางจากอาหาร F จุดบนช่องเดิน C ช่องมีเวลาประมาณ O(F×C)
และหน่วยความจำ O(F×C) เพราะกราฟเขาวงกตมีดีกรีไม่เกิน 4
MST ที่ใช้มีเวลา O(F²) ต่อชุดอาหารที่ยังไม่อยู่ใน cache
search ใช้ heap และอาจต้องเก็บสถานะจำนวนมากในกรณียาก
heuristic ลดจำนวนสถานะที่ต้องขยาย แต่ไม่ได้ทำให้ปัญหานี้มีต้นทุนต่ำในทุกขนาด

## 5. Project 1: Minimax เต็ม — `project1/minimax.py`

### 5.1 เหตุใดไม่ใช้ recursion แบบไม่มีเงื่อนไขหยุด

เกมเขาวงกตมีวงรอบ Pacman และผีอาจกลับมาที่ตำแหน่งเดิมโดยอาหารยังเหมือนเดิม
ถ้าใช้ minimax recursive จนถึงชนะ/แพ้อย่างเดียว อาจ recurse ไม่สิ้นสุด
ถ้าตัดที่ความลึกคงที่ ก็จะกลายเป็น H-Minimax
หากเจอวงรอบแล้วคืน 0 โดยพลการก็อาจเปลี่ยนคำตอบที่เหมาะที่สุด

โค้ดจึงสร้างกราฟสถานะที่มีจำนวนจำกัด แล้วแก้ค่า minimax ย้อนจากสถานะจบ
วิธีนี้เรียกว่า retrograde analysis

### 5.2 แปลงคะแนนเป็นต้นทุน

ส่วนนี้ใช้กับผีหนึ่งตัวและไม่มีแคปซูลตามขอบเขตการประเมิน
ถ้าอาหารเริ่มต้นมี F จุด อาหารเหลือตอนจบ R จุด และ Pacman เดินไป t ก้าว:

```text
C = คะแนนเริ่มต้น + 10F + 500
คะแนนเมื่อชนะ = C - t
คะแนนเมื่อแพ้ = C - (t + 1000 + 10R)
```

เราจึงลดต้นทุนแทนเพิ่มคะแนน:

- ขอบการเดิน Pacman มี cost 1
- ขอบการเดินผีมี cost 0
- ชนะมี terminal cost 0
- แพ้มี terminal cost `1000 + 10 × อาหารที่เหลือ`

Pacman เลือก **ต้นทุนต่ำสุด** ส่วนผีเลือก **ต้นทุนสูงสุด**
การเล่นไม่จบมีต้นทุน infinity เพราะคะแนนถูกหักต่อก้าวไม่สิ้นสุด

### 5.3 สร้างกราฟ

`key(state, turn)` รวมพิกัด Pacman, อาหาร, พิกัดผี, ทิศผี,
turn และสถานะชนะ/แพ้ โดยไม่ใส่คะแนนสะสม

`solve(initial)` ใช้คิวเดินกราฟและเก็บ:

| ตัวแปร | หน้าที่ |
|---|---|
| `seen` | สถานะที่รู้จักแล้ว ป้องกันวนสร้างกราฟ |
| `outgoing` | successor และ action ของแต่ละโหนด |
| `predecessors` | parent ที่จะได้รับผลเมื่อค่าของ child ถูกแก้แล้ว |
| `remaining` | จำนวน child ของฝ่ายผีที่ยังไม่รู้ค่า |
| `worst` | ค่า child ที่แพงที่สุดเท่าที่แก้แล้วของฝ่ายผี |
| `values` | cost ที่คำนวณเสร็จแล้ว |

ทุกรอบที่ขยายสถานะเกมเรียก successor API ตามผู้เล่น
สถานะที่ต่างกันแค่เวลาหรือคะแนนสะสมถูกรวมกันได้ เพราะต้นทุนอนาคตเหมือนกัน

### 5.4 แก้กราฟย้อนกลับ

1. ใส่สถานะจบลง min-heap ด้วย terminal cost
2. นำโหนดที่ cost ต่ำสุดออก ถ้าแก้ค่าแล้วให้ข้าม
3. กำหนดค่าของโหนดนั้น แล้วแจ้ง parent ทุกตัว
4. ถ้า parent เป็น Pacman มีทางเลือกหนึ่งที่แก้แล้วก็เสนอต้นทุนทางนั้นเข้า heap ได้
5. ถ้า parent เป็นผี ต้องรอ child ทุกตัว เพื่อรู้ทางที่แพงที่สุดก่อน
6. โหนดที่ยังแก้ไม่ได้หลัง heap หมดเป็นค่า infinity
7. สำหรับแต่ละโหนด Pacman เลือก action ที่ successor มี cost ต่ำสุด

การใช้คิว priority ปลอดภัยเพราะต้นทุนขอบไม่ติดลบ
และทุกวงรอบครบตาเกมมีขอบ Pacman ที่ cost เป็นบวก
จึงไม่ต้องเลือกค่าประเมินวงรอบขึ้นเอง

### 5.5 ขอบเขต

วิธีนี้หาค่า worst-case ตาม legal successors ได้ครบสำหรับเกมที่กำหนด
ไม่ได้รู้ชนิดผีจริง และไม่ได้รับประกันคะแนนที่ดีที่สุดหากรู้ล่วงหน้าว่าผีจะเดินพลาด
เป็นการเลือกสิ่งที่รับประกันได้แม้ผีเลือกการตอบโต้ที่แย่ที่สุด

ต้องสร้างกราฟทั้งหมด จึงมีต้นทุนสูงบนแผนที่ใหญ่หรืออาหารจำนวนมาก
ใช้กับ `small_adv` ตามโจทย์; กรณีแคปซูลจะแจ้งว่าอยู่นอกขอบเขต
การเก็บทิศผีใน key เป็นสิ่งจำเป็นต่อความถูกต้อง

## 6. Project 1: H-Minimax — `project1/hminimax.py`

### 6.1 จำกัดความลึกเป็น “รอบ”

ค่า default depth คือ 4 หมายถึง Pacman เดินและผีตอบจนครบสี่รอบ
depth ลดเมื่อจบตาผี ไม่ลดทั้งสองตาพร้อมกัน
สถานะที่ชนะ/แพ้หยุดได้ทันที แม้ยังไม่ครบ depth

### 6.2 ประเมินปลายต้นไม้

สำหรับสถานะยังไม่จบ:

```text
evaluation = score
             - 12 × จำนวนอาหารที่เหลือ
             - 2 × ระยะในเขาวงกตถึงอาหารใกล้สุด
             - 12 / max(ระยะในเขาวงกตถึงผี, 0.5)
             - 2 × จำนวนครั้งที่เคยเจอ (ตำแหน่ง, ชุดอาหาร) นี้
```

แต่ละพจน์มีเหตุผล:

- คะแนนจริงเก็บรางวัลและค่าปรับของเกม
- อาหารที่เหลือกระตุ้นให้มีความคืบหน้า
- ระยะอาหารช่วยบอกทิศแม้อาหารยังอยู่นอก horizon
- ระยะผีลดแรงจูงใจให้เข้าใกล้อันตราย
- การเยือนซ้ำลดอาการเดินวนโดยไม่เก็บอาหารเพิ่ม

ชนะได้ `100000 + score` แพ้ได้ `-100000 + score`
ค่าคงที่นี้ตั้งให้สถานะจบมีอิทธิพลเหนือ heuristic ในแผนที่ของงาน
จึงเป็นการออกแบบ heuristic ไม่ใช่บทพิสูจน์ว่าผลดีที่สุดในทุกแผนที่หรือทุกช่วงคะแนน

### 6.3 Alpha-beta pruning

`alpha` เก็บค่าที่ Pacman รับประกันได้อย่างน้อยแล้ว
`beta` เก็บขอบบนที่ผียอมให้เกิดจากทางเลือกที่ตรวจไป
เมื่อ `alpha >= beta` การตรวจทางเลือกที่เหลือไม่เปลี่ยนการตัดสินใจของบรรพบุรุษ
จึงหยุดขยายสาขานั้นได้

เรียง successors ด้วย evaluation ก่อนค้น:
ฝ่าย Pacman เริ่มค่าดูดีมากก่อน ฝ่ายผีเริ่มค่าดูแย่มากก่อน
ช่วยให้เจอขอบ alpha/beta ที่ตัดสาขาได้เร็ว

## 7. Project 2: แบบจำลอง — `project2/bayesfilter.py`

### 7.1 นิยาม belief

สำหรับผี g:

```text
b_g[x, y] = ความน่าจะเป็นที่ผี g อยู่ช่อง (x, y)
```

ผีที่ยังไม่ถูกกินมีผลรวม 1 และมีมวลบนกำแพงเป็น 0
ผีที่ถูกกินแล้วใช้เมทริกซ์ศูนย์ทั้งหมดตามโจทย์
ใช้ list ของเมทริกซ์เพื่อรองรับหลายผีที่ใช้ policy เดียวกัน

### 7.2 แบบจำลองเซนเซอร์

โค้ดเดิมใช้:

```text
p = 0.5
n = int(sensor_variance / (p × (1-p))) = floor(4 × sensor_variance)
K ~ Binomial(n, 0.5)
evidence = ManhattanDistance(ghost, Pacman) + K - n/2
```

ระยะที่อ่านได้มีค่าเฉลี่ยเท่าระยะจริงและมีความแปรปรวนจริง `n/4`
ค่าที่ตั้งไม่จำเป็นต้องเท่าความแปรปรวนจริงเพราะมีการตัดเป็นจำนวนเต็ม
เมื่อ n เป็นเลขคี่ ค่าที่อ่านอาจเป็นครึ่งจำนวนเต็ม และอาจติดลบใกล้ Pacman
จึงไม่ควร round หรือ clip evidence

`_get_sensor_model(pacman_position, evidence)` คำนวณระยะทุกช่องพร้อมกัน
ด้วย broadcasting จากนั้นแปลงเป็นจำนวน successes:

```text
k = evidence - distance + n/2
likelihood = binom.pmf(k, n, 0.5)
```

ถ้า k ไม่ใช่จำนวนเต็มที่อยู่ใน `[0, n]` ความน่าจะเป็นคือศูนย์
กำหนดค่าบนกำแพงเป็นศูนย์อีกชั้นหนึ่ง

### 7.3 แบบจำลองการเดินผี

กำหนด q เป็นพารามิเตอร์เดียว:

| ชนิดผี | q | น้ำหนักทางที่ไม่เข้าใกล้ Pacman | น้ำหนักทางเข้าใกล้ |
|---|---:|---:|---:|
| confused | 0 | 1 | 1 |
| afraid | 1 | 2 | 1 |
| scared | 3 | 8 | 1 |

สำหรับทุกช่องเริ่ม x หาเพื่อนบ้านที่ไม่ใช่กำแพง
ให้ weight `2^q` เมื่อระยะใหม่ไม่น้อยกว่าระยะเดิม มิฉะนั้นให้ 1
หารด้วยผลรวมน้ำหนักของเพื่อนบ้านทั้งหมด
ตัวอย่างสองทางหนีและสองทางเข้าใกล้:
ผี scared เลือกกลุ่มทางหนีด้วยความน่าจะเป็น `16/(16+2) = 8/9`

Project 2 ยอมให้ผีกลับหลังหัน ต่างจาก Project 1
ช่องที่ไม่มีเพื่อนบ้านเลยให้ self-transition 1 เพื่อให้ distribution สมบูรณ์

`_get_transition_model()` คืนอาร์เรย์ 4 มิติ ตามสัญญาของโจทย์:

```text
T[new_x, new_y, old_x, old_y]
```

ผลรวมเหนือสองแกนแรกของช่องต้นทางที่เดินได้ต้องเท่ากับ 1
ต้นทางที่เป็นกำแพงมีค่าเป็นศูนย์ทั้งหมด
cache โมเดลเมื่อ Pacman ยังอยู่ตำแหน่งเดิม และสร้างใหม่เมื่อ Pacman ย้าย

แบบจำลองนี้อธิบายการเคลื่อนที่ก่อนเกิดการกินผี
engine จริงย้ายผีที่ถูกกินไปพิกัดนอกกระดาน;
filter ใช้ eaten flags เพื่อคืนศูนย์แทนการติดตามพิกัดนั้น
นอกจากนี้ ghost code เดิมคำนวณน้ำหนักผ่าน successor ที่อาจเกิดการกินแล้ว
จึงมีความต่างที่ขอบเหตุการณ์ชนกับแบบจำลองการเดินเชิงเรขาคณิต
การทดลอง tracking ปิด collision เพื่อแยกวัดแบบจำลองการเดินที่ระบุในสมการ
การทดสอบเกมจริงตรวจการกินผีและ controller เพิ่มต่างหาก

### 7.4 Predict → Correct → Normalize

สำหรับแต่ละผี:

```text
prediction[y] = sum_x T[y, x] × prior[x]
unnormalized[y] = sensor_likelihood[y] × prediction[y]
posterior[y] = unnormalized[y] / sum_y unnormalized[y]
```

`_get_updated_belief()` เรียกสองฟังก์ชันโมเดลที่โจทย์กำหนด
แล้ว reshape transition เป็น matrix โดยแกนปลายทางอยู่ก่อนต้นทาง
เลือกเฉพาะ entries ที่ไม่เป็นศูนย์ และใช้ `np.bincount` รวมมวลที่มาถึงปลายทางเดียวกัน
ผลเท่ากับ dense matrix multiplication แต่ไม่คูณศูนย์ทุกตัวต่อผี

ใช้ sensor model ร่วมกันสำหรับผีที่มี evidence เท่ากันในรอบนั้น
แต่ belief ของแต่ละผียังคงแยกกัน ไม่มีการเฉลี่ย belief รวมจนสูญเสียตัวตนผี

อาร์เรย์ transition 4 มิติยังใช้หน่วยความจำ O(N²) ตามสัญญาของโจทย์
N คือจำนวนช่องทั้งกระดาน การหา nonzero แต่ละ update ยังต้อง scan O(N²)
ส่วนการกระจายมวลต่อผีเป็น O(E) ซึ่ง E ไม่เกินประมาณสี่เท่าจำนวนช่องเดิน
จึงเหมาะกับขนาดแผนที่ที่ให้มา แต่ไม่ควรอ้างว่าทั้งโมเดลใช้พื้นที่เชิงเส้น

### 7.5 กรณีที่ posterior รวมเป็นศูนย์

อาจเกิดจาก prior เป็นศูนย์ หรือ evidence ขัดแย้งกับโมเดล/ข้อมูลเริ่มต้น
โค้ดใช้ลำดับ recovery:

1. ลอง likelihood บน prior แบบ uniform ของช่องเดิน
2. ถ้า observation เป็นไปไม่ได้ทุกช่อง ใช้ prediction ที่ยังมีมวล
3. ถ้า prediction ก็ไม่มีมวล ใช้ uniform บนช่องเดิน

ทำให้ไม่หารศูนย์หรือสร้าง NaN
นี่เป็น recovery เมื่อข้อมูลไม่สอดคล้อง ไม่ใช่ Bayes posterior ที่นิยามได้จากเหตุการณ์ probability zero
สำหรับข้อมูลปกติใช้สมการ Bayes โดยตรง

## 8. Metrics และการทดลอง

`_record_metrics()` เข้าถึงตำแหน่งจริงเพื่อประเมินผลเท่านั้น
สำหรับผีที่ยังมี belief บันทึก:

| Metric | สมการ/ความหมาย | ทิศทางที่ดี |
|---|---|---|
| entropy | `-sum b(x) log2 b(x)` | ต่ำ = มั่นใจมากขึ้น |
| Brier | `sum (b(x) - 1[x=truth])²` | ต่ำ = distribution ใกล้ความจริง |
| true_mass | `b(truth)` | สูง = ให้โอกาสตำแหน่งจริงมาก |
| expected_distance | `sum b(x) × Manhattan(x, truth)` | ต่ำ = มวลอยู่ใกล้ตำแหน่งจริง |

Entropy ต่ำไม่ได้แปลว่าถูก เช่น มั่นใจว่าผีอยู่ผิดมุมก็มี entropy ต่ำ
จึงต้องใช้ metric คุณภาพอย่าง Brier ประกอบกัน
expected_distance ใช้ Manhattan เพื่อสื่อความคลาดเคลื่อนตำแหน่ง
ไม่ใช่จำนวนก้าวที่ Pacman ต้องใช้หลบกำแพงไปจับผี

### 8.1 ทำไมทดลองหลายครั้งและใช้ confidence interval

ตำแหน่งเริ่ม การเคลื่อนที่ และ sensor noise ล้วนสุ่ม
เส้นจากเกมเดียวอาจดูดีหรือแย่เพราะความบังเอิญ
จึงทดลอง 30 trials และเฉลี่ย 3 ผีภายในแต่ละ trial ก่อน

ช่วงความเชื่อมั่นที่ใช้คือ:

```text
mean ± t(0.975, trials-1) × sample_std / sqrt(trials)
```

หน่วยอิสระที่นำมาคำนวณคือ trial ไม่ใช่ทุก time step
เพราะข้อมูลตามเวลาภายใน trial มีความสัมพันธ์กัน
error bars เป็น pointwise 95% confidence intervals ไม่ใช่ขอบเขตรับประกันทุกจุดพร้อมกัน

### 8.2 การจำลอง ground truth

`TrackingObservation` เป็น adapter ที่ให้เมธอดที่ ghost policy เดิมต้องใช้
ส่งเข้า `ConfusedGhost`, `AfraidGhost`, `ScaredGhost` จาก engine เดิม
เพื่ออ่านความน่าจะเป็นการเดิน ไม่สุ่มจาก transition matrix ของ filter เอง
จึงลดโอกาสที่โมเดลผิดเหมือนกันทั้งตัวสร้างข้อมูลและตัวประมาณแล้วดูเหมือนผ่าน

adapter ใช้พิกัดหลังเดินตามเรขาคณิตและไม่ทำ collision
Pacman อยู่ตำแหน่งเริ่มต้นและทุก trial ยาวเท่ากัน
นี่เป็นการทดลองควบคุมการติดตาม ไม่ใช่เกมโบนัสที่มีการกินผี

ใช้ random generator แยกสำหรับ motion และ sensor
การเปลี่ยน variance จึงไม่เปลี่ยนเส้นทางผีเพียงเพราะใช้ random number ต่างจำนวนกัน

### 8.3 ตรวจความนิ่งของผล

ค่าเฉลี่ยปลายการทดลองคำนวณจากหนึ่งในสามช่วงท้าย
เปรียบเทียบกับหนึ่งในสามก่อนหน้านั้นด้วยผลต่างแบบจับคู่ trial
บันทึกทั้งผลต่างและ confidence interval ของผลต่าง

### 9.3 การให้คะแนน action

สำหรับทุก action ที่เดินได้จริง:

1. คำนวณตำแหน่งปลายทาง z
2. ทำ BFS บนแผนที่ชั่วคราวจาก z
3. รวมมวล belief ของผีทุกตัวแบบลดน้ำหนักตามระยะ
4. ให้โบนัสโอกาสเจอผีทันทีที่ z
5. หักคะแนนการไปซ้ำช่องที่เคยเยือนบ่อย

```text
utility(z) = sum_g sum_x belief_g(x) × exp(-estimated_distance(z,x)/4)
             + 2 × sum_g belief_g(z)
             - 0.03 × visits(z)
```

เลือก utility สูงสุดใน legal moves เท่านั้น
ถ้าไม่เหลือการเดิน ใช้ STOP
ถึงแม้แผนที่ชั่วคราวจะคิดว่ากำแพงที่ยังไม่พบเดินผ่านได้
การเดินจริงหนึ่งก้าวก็ยังถูกตรวจจาก legal actions ของ engine ทุกครั้ง

ตัวคูณ 4, 2, 0.03 เป็นพารามิเตอร์ heuristic ที่ใช้ในการทดสอบนี้
ไม่มีข้อพิสูจน์ว่าจับผีเร็วที่สุดหรือรับประกันชนะทุก seed

## 12. ข้อจำกัดที่ควรอธิบายได้ตอนนำเสนอ

1. BFS เหมาะที่สุดตามจำนวนก้าว แต่แคปซูลทำให้คะแนนอาจด้อยกว่า A*
2. Exact Minimax ถูกออกแบบสำหรับผีหนึ่งตัว ไม่มีแคปซูล และพื้นที่สถานะไม่ใหญ่เกินไป
3. H-Minimax แลกการรับประกันคำตอบดีที่สุดกับการคำนวณที่น้อยลง
4. Bayes filter ใช้โมเดล noise และ policy ที่โจทย์ระบุ ถ้าเปลี่ยนโมเดลจริงต้องปรับตาม
5. ฟังก์ชัน transition คืน dense tensor ตามสัญญาโจทย์ จึงมีข้อจำกัดหน่วยความจำ
6. recovery เมื่อ evidence เป็นไปไม่ได้เป็นวิธีทำให้รันต่อได้ ไม่ใช่หลักฐานว่าข้อมูลถูกต้อง
7. กราฟ tracking เป็นการทดลอง Pacman นิ่ง ต้องแยกจากผล controller ในเกมจริง
8. ผ่าน tests ที่มีอยู่ยังไม่ยืนยันผลจากแผนที่ลับของอาจารย์
